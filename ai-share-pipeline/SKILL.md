# AI 经验分享流水线（截图 + 口述 → 图文 + 视频）

## 这个技能解决什么

用户攒了一批"用 AI 的过程截图"，脑子里有讲解思路，想把它变成能发出去的分享内容——**图文**（公众号 / 小红书）和**视频**（B 站 / 视频号）都要。

痛点是重复劳动：图文写一版、视频又写一版脚本，改个内容两边同步很累。

**这个技能的核心决策：图文稿本身就是"统一源"。** 先把内容做成一篇图文稿（`article.md`），图文直接发；要视频时，把**同一篇稿子**喂给 `web-video-presentation` 技能，截图作为素材挂进去。零新增中间格式，一份稿子两用。

> 为什么不另造一个"分镜脚本"中间层？因为 `web-video-presentation` 自己就会把文章切成章节/节拍并重排节奏，你手写的分镜节点不会 1:1 存活，反而多维护一层。图文稿当源最省事。

---

## 输入（开工前必须拿到）

技能起不来就问用户要这两样，别硬编：

1. **截图文件夹的绝对路径**（如 `/Users/xxx/Desktop/ai-demo-shots`）
2. **口述讲解思路**：这次分享哪段 AI 经验、想让读者 get 到什么、大致分几块讲。几句话或一段语音转文字都行。

还要问清**目标平台**（决定图文形态，见 Phase 2）：
- 公众号 → 长文，图穿插在段落里
- 小红书 → 轮播图 + 短正文，一张图承载一个要点
- 两个都要 → 先做公众号长文当主稿，小红书从主稿裁

---

## Phase 1 — 整理截图（定序是关键，别靠文件时间）

**核心原则：截图顺序 = 讲解逻辑顺序，不是文件创建时间。**

用户往往先截了后面的步骤、后补前面的图，所以"按添加时间排"会错乱。正确做法：

1. **看图内容**：逐张读截图，理解每张在讲什么（哪个界面、什么操作、什么结果）。
2. **对齐口述思路**：把图匹配到用户口述的逻辑节点上。
3. **文件时间只作辅助**：macOS 截图文件名自带时间戳（`Screenshot 2026-01-01 at 10.30.png`），当同一逻辑步骤有多张图时，用时间戳定它们的先后。**不需要重命名文件**——时间戳已经有序。

产出一个**截图清单**给用户过目（顺序 + 每张一句话作用），例如：

```
① login-panel.png      —— DeepSeek API key 填写界面
② first-prompt.png     —— 第一次提问，回答偏泛
③ refined-prompt.png   —— 加了角色设定后，回答变具体（对比②）
...
```

用户确认顺序对了再往下。**顺序错了，后面全错**，这一步值得停一下。

---

## Phase 2 — 写图文稿 `article.md`（统一源）

在**用户当前工作目录**下建 `article.md`。这是整个流程的源文件，图文和视频都从它来，**别删**。

**写作要点：**

- **结构跟着口述思路走**，不是跟着截图堆。先有逻辑骨架（几个部分、每部分讲什么），截图作为"证据"挂到对应位置。
- **定点插图 = 完成截图绑定**。在正文里用 markdown 图片语法把截图放到它讲的那段旁边：`![DeepSeek API 填写界面](./shots/login-panel.png)`。这一步同时服务图文（读者看图）和视频（后面当素材）。
- **信息密度要够图文正文用**。一句话要点撑不起公众号段落——每个节点展开成能读的段落（背景 + 做了什么 + 结果 / 踩的坑 / 心得）。这是图文和视频的真实差异：视频靠口播节拍可以短，图文得扩写。
- **说人话**：用平实语言讲清楚，专业概念先给一句大白话再上术语。避免 AI 味（详见下方反 AI 味）。

**平台形态：**

| 平台 | 形态 | 写法 |
|---|---|---|
| 公众号 | 长文 | 完整段落 + 图穿插，可用小标题分节 |
| 小红书 | 轮播图 + 短正文 | 每个要点 = 一张卡片（可复用截图或让 AI 做图），正文精炼 + 标签 |

**排版发布**：公众号排版可接 `md2wechat` 技能；小红书轮播图可接 `content-pipeline` 技能。本技能负责内容，排版交给它们。

写完 `article.md` **停下来**给用户验收：稿子逻辑对不对、图放对没有、哪段太薄/太厚。用户 OK 了，**图文就能直接发了**。

---

## Phase 3 — 桥接视频（同一篇稿子，可选，后补）

用户要视频时，**不重写内容**，直接调 `web-video-presentation` 技能，把 `article.md` 当它的输入文章。

交接给 `web-video-presentation` 时明确告诉它：

1. **输入文章** = 本流程产出的 `article.md`（它会保留为画面信息源）。
2. **真素材** = 截图文件夹。在它的 **Checkpoint Plan 第 4 步（素材）** 把截图挂进去——需要"看真实界面"的章节用截图，抽象概念/流程让它用 CSS 现画。
3. **混合动效是底线，不是可选项**。`web-video-presentation` 每章强制至少 1~2 处视觉演示（纯贴图纯文字的章节它会打回）。所以别指望"每屏就贴一张截图"——那会撞它的自检。规划时就按"截图 + CSS 动效混合"来。
4. 剩下的（口播稿、切章、主题、TTS 配音、录屏）都交给 `web-video-presentation` 的标准流程，本技能不重复它。

**产物顺序建议**：图文先发（回款/曝光快），视频后补。同一批内容两个平台形态，改一次源稿两边都能重出。

## 贯穿全程的原则（来自实测复盘）

| 原则 | 为什么 |
|---|---|
| 截图定序靠内容+口述，不靠文件时间 | 用户常后补前面的图，时间会乱；内容才是真顺序 |
| 图文稿即统一源，不造分镜中间层 | web-video-presentation 会自己重切节奏，手写分镜白搭，多一层维护 |
| 定点插图同时完成图文展示和视频素材绑定 | 一个动作两用，不重复标注 |
| 图文正文要扩写，别照搬口播密度 | 视频靠节拍可短，图文段落撑不起就没法读 |
| 视频侧走混合动效 | 纯截图会撞 web-video-presentation 的每章视觉自检 |
| 图文先发、视频后补 | 回款快，且视频从已验收的稿子倒推更稳 |

## 反 AI 味（图文写作时）

- 不堆"赋能""闭环""绦密"式空词，不无脑三段排比，不滥用破折号
- 少用"首先/其次/然而/总而言之"这类连接词开头
- 结论直给，不写"正确但没用"的废话
- 需要时可接 `humanizer-zh` 技能做去 AI 味
