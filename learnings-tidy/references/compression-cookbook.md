# 压缩手法册（Step 3 动手前读一次；同族合并拿不准时回读）

压缩是「删冗、合并、留真」三件事。**目标不是最短，是「信息点一个不少、字数尽量低」。**
判断一条内容该不该留，只问一句：

> 读者下次触发这个坑时，靠新文件能不能定位并修好？能 → 可精简；不能 → 保留原文关键串。

下面四类手法是**可执行的操作定义**，不是口号。每类都给判据与反例。

---

## 先定义「硬事实」（本技能的核心判据）

- **算硬事实**（合并时必须保留**每个同族里各条独有**的这些，重复的才去重）：
  报错原文（含引号/冒号的原始报错串）、完整命令（含参数/选项、≥2 个 token）、绝对路径、URL、
  端口号、版本号、数字+单位（「≥3 次」「5+ 文件」）、文件名。
- **不算硬事实**（可随案例叙述删）：变量占位符（`$VAR`、`${arr[@]}`、`${=A}` 这类纯语法示例）、
  单个通用命令词（`ls`/`grep`/`git`/`python3`）、残缺片段（`, TodoWrite`、`...）EOF`、`-o`）。
- **合并纪律一句话**：**合并同族 = 合并叙述，不是合并事实**——该族各条独有的硬事实必须
  **全部迁到**合并后的那一条里。

> 为什么要划这条线：把 `$VAR`/`-o` 这类语法片段也当事实，压缩必然「大减幅」，抽查却全是噪音；
> 反过来漏掉某条独有的报错串/权限配置值，就是真丢信息。判据划清，覆盖率才有意义。

---

## 手法 ① 合并同族

**什么算同族**：同一主题 / 同一根因 / 同一修法，出现 ≥2 条。用 `family_report.py` 的关键词分桶
给出候选，**最终由人确认**（脚本只给数字与候选，不做判断）。

**合并后保留谁的措辞**：不选「更好看的那条」，而是**把每条的硬事实全部抄进存活条**——
存活条 = 标题最通用、或最早出现的那条。正文取「现象 → 根因 → 规则」三段式，
硬事实（报错原文、命令、路径、端口、版本号、数字口径）逐条并入，**一条都不能省**。

**判据**：合并族的每一条独占硬事实，在合并后都能 `grep -F` 命中。数量对不上就是合错了。

**例**：`子代理 16k 输出上限` 8 条（4 次实锤版 / 15 行版 / 报错原文版 / 恢复方法版…）
→ 1 条，逐条要点保留（硬约束写法、软限制拦不住、只读代理必崩、判据、恢复）。

---

## 手法 ② 去模板元数据

self-improvement 模板的记账字段与条目内容无关，是压缩收益最大的地方：

**删**（六类记账字段 + 格式化小标题）：

```
**Logged**: …    **Priority**: …    **Status**: …
**Area**: …      **Context**: …
**Metadata**: …  （含 Reproducible / See Also 等）
#### Summary / #### Error / #### Context / #### Suggested Fix  （小标题本身）
```

**必须留的两类**（藏在元数据里的硬事实，删字段前先把内容搬进正文）：
1. **`Error:` / ``` 代码块里的报错原文**——这是硬事实，删的是围栏不是内容。
2. **`Related Files:` / 路径 / 版本号 / 端口**——凡带具体值的一律先搬进正文再删字段。

**判据**：压缩后 `grep -E '^(Logged|Priority|Status|Area|Context|Metadata)' <新文件>` 无输出，
而原 `Error` 块里的报错原文仍能 `grep -F` 命中。

## 手法 ③ 精简表述

**保留三段骨架**：现象 → 根因 → 规则/修法。这三样少一样，条目就失效了。

**砍**：复现过程、排查流水账、「我怎么想到的」推理过程、重复举例、情绪化描述、
多条同义表述里多余的那几条。

**不砍**：报错原文（含引号/冒号的原样串）、命令行（逐字含参数）、绝对路径、
端口/版本号、数字口径（阈值、次数、比例）、现象里那句能唯一指向病根的措辞。

**例**：一条 30 行的复现记录 → 3 行：「现象句 + 根因句 + 规则句」，报错原文原样保留。

---

## 手法 ④ 重建顶部「反复踩过的（≥3 次）」摘要

顶部摘要是给「开工前 30 秒扫一眼」用的，压缩后要按新内容**重算**，不能照抄。

- 只收**实证 ≥3 次**的条目；次数写进括号（如「8+ 次实锤」）。
- 每条一行，写完去看它对应的正文条目还在不在——摘要指向不存在的正文就是坏指针。
- **原文没有顶部摘要就不硬造**；原文有就保留并更新。

---

## 反例：合并会失真 / 丢边界的四种情形（宁可留着，别合并）

1. **互相推翻的更正链**：三条约 ×「重试就好」→「令牌过期」→「用户中途换了令牌」，
   合并成一条会把「证据如何演化」压掉，读者拿到一个被后续更正推翻的结论。
   → 只留**最终正确**那条，正文补一句「曾误判为 X」，别把前两条的措辞并进来。

2. **同族但适用边界不同**：zsh「通配无匹配中止」与 zsh「变量不拆词」根因相近，
   但触发条件与修法都不同。→ 合并会丢边界，**保留两条**。

3. **全局 vs 项目专属**：同一条经验在全局与项目里各有一份、细节不同。
   → 全局只留跨项目可复用的部分；项目专属细节**迁往项目根**（列入报告的「待迁移」），别硬合。

4. **合并后措辞二选一会丢硬事实**：两条各有独特端口/版本，合并只能留一条的措辞。
   → 硬事实必须**全部**抄进合并条；做不到就说明这两条不该合。

---

## 止损线（防止把规则也砍掉）

- 字节减幅经验区间 **55%–80%**（三次实证 -65% / -67% / -76%）。
- **超过 85% 即触发复核**：大概率砍进了规则本体或硬事实，回看 `coverage_check` 的缺失清单。
- 硬判据：压缩前后各跑一次指纹，**硬事实计数只增不减**；条目数可降（合并所致），
  但每个被合并族至少有一条存活条目。
