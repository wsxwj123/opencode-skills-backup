## 0. 先说矛盾：BRIEF 里我不能默默替你选的地方

开工前必须拍板的 6 条。每条给出我的建议和理由，但**需求归你，不是我改 BRIEF**。

### 0.1 存量积压的真实数量不是 72，也不是 99，是 87

BRIEF 写"72/103 是待定或待确认"、F6 写"存量 99 个分诊"。实扫结果：

| 口径 | 数量 |
|---|---|
| `user_verdict` 精确等于 待定/待柚子确认/pending | 75 |
| 再算上 `待定：拟作 2027 青基主线方案 A` 这类"占位词+补充说明"的变体 | **87** |
| 已有真实裁决（`不建议作主课题`、`已否决（…）`、`建议立即纳入工作流` 等） | 16 |

建议：以 87 为准，用"前缀/整串匹配占位词"这一条规则判定未裁决。那 16 条虽然不是"采纳/否决/归档"三个字，但明显是你本人下过的判断，**分诊不该再动它们**，否则等于让你把已经做过的决定重做一遍。

### 0.2 "单轮"脚本感知不到，我用"单个日历日"代替

F5 说"单轮种子 ≤8、深度展开 ≤3"。脚本没有"一轮"这个概念——会话可以开一整天，也可以一小时开三次。可验证的唯一代理是日历日。

建议：改成 **每个自然日最多注册 8 个种子、最多写入 3 个深度假说**。理由：BRIEF 记录的病症原文就是"2026-09-15 一天产出 47 个想法"，日上限直接对症；而且无状态、可复现、测试能断言。

代价说清楚：你一天里真想开第二轮，第 4 个假说会被硬拒。**不提供 `--force` 绕过**（留了口子就等于没有闸门）。要放宽就改脚本里那一行常量，改完自己知道自己放宽了。

### 0.3 "入库"和"裁决"我合并成一次写入

F3（写回门禁）和 F4（零积压）读起来像两步：先入库，再裁决。但只要允许"先入库、裁决待补"，积压就会立刻重新长出来——现有 87 格就是这么来的。

建议：**没有终态裁决的假说根本进不了库**。`commit` 必须同时带 `user_verdict ∈ {采纳, 否决, 归档}`。零积压从"定期检查"变成"结构上不可能积压"。

你想"先放着回头再想"的场景，由 `归档 + 重启条件` 承接——这正是 BRIEF F4 给归档设计的用途。

被我否掉的替代方案：在地图外另建一个 pending 队列。否掉的理由是 BRIEF 明确禁止"迁移地图出现两个写者"，pending 队列就是第二个写者，而且它会变成新的积压池。

### 0.4 SKILL.md 现有的"实验设计"一节和 F2 打架

F2 要求"研究思路与设计只写到大概的实验内容，不出独立详细实验方案"。但 SKILL.md 第 118-128 行有完整的一节《实验设计》，包含假设/关键对比/读出指标/对照/证伪点。

建议处理：**不删，降级为按需触发**。改成"用户明确点名要最小方案时才做"，默认流程不进这一节。同时把其中"证伪点要落到承重变量+非同义反复对照"那段**移到假说体例里**——因为证伪点在本次改造中成了写回必填项，它已经属于假说的组成部分，不再属于实验设计。

理由：那段证伪点的写法是整份 SKILL.md 里最硬的东西（真实数据里只有 3/103 做到，但做到的那 3 条质量明显高于其余），删了是净损失；留在原地又会诱导 AI 每次都出详细方案，违反 F2。

### 0.5 零积压闸会在存量清完之前把技能锁死

闸门一上线，87 格未裁决 → 任何新产出都被拒 → idea-bomb 当场不可用，直到 F6 分诊跑完。

建议：这是**特性不是 bug**，但要明确上线顺序：分诊命令不受零积压闸约束（它是解药，不能被病挡住）。上线当天第一件事就是跑 F6。方案已按此设计。

### 0.6 "查新证据必填"和真实数据里合法的"未检索到"冲突

F3 要求 `closest_work + diff` 必填。但真实数据里有 5 条合法写法是 `未见先例`（4 字）、`无直接先例`（5 字）、`未检索到直接工作`（8 字），SKILL.md 第 102 行也明确允许"检索未见直接先例"。同时又有 `diff` 只写 `—` 或 `无` 的敷衍条目（idx=44/45/75）和 `diff` 直接是 `None` 的（idx=57/58）。

一刀切的最小长度会把合法的和敷衍的一起砍。建议改成**条件规则**：

- `closest_work` 声明"未检索到先例"时，`diff` 可以留空——但必须提供 `novelty_queries`（你实际跑过的检索式），否则视为空口声称。
- `closest_work` 写了具体工作时，`diff` 必填且 ≥10 字。

这条规则是读真实数据读出来的，不是拍脑袋定的。

## 1. 改造总览

### 1.1 一句话

把 SKILL.md 里已经写对但没人执行的规则，能落到脚本上的全部落到脚本上；落不到的，明确标成"只能劝"，不假装它是闸门。

### 1.2 SKILL.md 怎么改

**保留不动**（这些是技能的灵魂，本次改造和它们无关）：

- YAML frontmatter（触发词、description）——只在 description 末尾补一句两段式说明
- 《交付时说人话》整节，含 AI 腔对照例
- 《数据与工具》《首次使用，先定调》
- 《两轴》整节（创新性/可行性三层/甜区 2×2）
- 《红线》《冷启动的实情》《反面清单》

**改**：

| 位置 | 改法 | 为什么 |
|---|---|---|
| 核心循环 Step 0 | 加"开工第一件事：跑零积压闸，被拒就先清积压" | F4 |
| 核心循环 Step 3-6 | 拆成两段：**第一段**只出 ≤8 个一句话种子，不查新、不打分、不入库；用户点选 ≤3 个后进**第二段**，才做两轴、查新、写假说、入库 | F1/F5 |
| 核心循环 Step 6 | 从"问用户怎么判断、写回"改为"调 commit 脚本写回，脚本拒了就照报错补，禁止手改 JSON" | F3/F4 |
| 实验设计一节 | 降级为按需触发；证伪点那段移入 references/hypothesis-format.md | 0.4 节 |
| 迁移地图一节 | 示例 JSON 更新为 schema 2；补一句"老格子是 schema 1，读得懂就行，不回填" | 老数据兼容 |

**加**：

- 一节《四个闸门》：每个闸门在流程的哪一步、调哪条命令、被拒了怎么办。**只写调用点和一句话规则，详细判定规则放 references/gates.md**
- 一节《两段式产出》：第一段和第二段各自的产物形态、禁止事项
- 一节《摘要式假说》：四要素是什么，详细体例指向 references/hypothesis-format.md

### 1.3 脚本加几个、各管什么

两个，不是四个。按"碰不碰核心数据"切开：

| 脚本 | 职责 | 碰什么数据 |
|---|---|---|
| `scripts/ib_map.py` | **唯一的迁移地图写入通道** + 只读查询。子命令：`status` / `gate` / `commit` / `verdict` | 读写 `migration_map.json`（高危，全部写入走备份+原子写） |
| `scripts/ib_seed.py` | 第一段种子登记与查询。子命令：`register` / `list` | 只读写 `~/.idea-bomb/session/seeds-<日期>.json`（一次性会话文件，坏了无所谓） |

`scripts/zotero_read.py` 不动。

为什么不拆成四个脚本（一个闸门一个）：备份 + 原子写 + 占位词判定这套逻辑会被复制四份，改一处忘三处。按数据归属切，碰核心资产的代码集中在一个文件里，好审计。

为什么不合成一个脚本：session 文件是可丢弃的临时态，迁移地图是不可丢的核心资产。混在一个文件里，日后改 session 逻辑时手会抖到地图那边。

## 3. 四个闸门：哪些真能拦，哪些只能劝

**先说整套设计最大的窟窿**：所有脚本闸门都建立在"AI 通过脚本写库"这一前提上。执行技能的 AI 完全可以用 Edit 工具直接改 `migration_map.json`，一刀绕过全部四个闸门。这个窟窿**堵不上**，只能做两件事：

1. SKILL.md 里写死禁令："迁移地图只能由 `ib_map.py` 写，禁止任何形式的直接编辑"——这是劝，不是拦。
2. 在地图里存一个 `_integrity` 审计字段（写入次数 + 上次写入后的文件 sha256）。任何脚本下次运行时重算，对不上就在 stderr 报"检测到绕过脚本的外部写入"。**这是事后发现，不是事前阻止**，但能把隐形绕过变成可见绕过。

BRIEF 的核心判断是"规则写了但没强制手段"。下面这张表就是诚实版的强制手段清单。

| 闸门 | 规则 | 强制等级 | 拦得住什么 | 拦不住什么 |
|---|---|---|---|---|
| **闸门 1 数量闸** | 种子 ≤8/日；深度假说 ≤3/日 | **脚本硬拦** | 第 9 个种子注册被拒；当天第 4 个 commit 被拒（退出码 2） | AI 在对话里口头列 20 个种子只登记 8 个。脚本只保证"进得去的不超 8"，不保证"说出口的不超 8" |
| **闸门 2 写回必填闸** | 四要素齐全 + 三层可行性 + 证伪点 + 查新证据 | **脚本硬拦字段的"形"，拦不住"实"** | 缺字段、空字符串、纯空白、占位词、低于最小长度、`feasibility_layers` 不足 3 层、`method=transfer` 却只跑了 1 条检索式——全部拒绝写入 | 内容真不真、质量高不高。AI 可以给每个要素编 30 个字的空话照样过闸。`novelty_queries` 里写的检索式**脚本无法验证是否真的跑过** |
| **闸门 3 零积压闸** | 库中有未裁决项就不许产出新想法 | **脚本能判定，拦不住"不调用"** | `ib_map.py gate` 在积压 >0 时返回退出码 2 和未裁决清单。凡是跑了这条命令的流程都拦得住 | AI 跳过这条命令直接开始想点子。这一步的强制力**完全依赖 SKILL.md 把它写成 Step 0 的第一条**。这是四个闸门里最弱的一个，必须承认 |
| **闸门 4 裁决终态闸** | 只接受 采纳/否决/归档；归档必带重启条件 | **脚本硬拦** | 写 `待定`、`待柚子确认`、`pending`、`TBD`、`搁置`、空串、`—` 全部拒绝；归档不带重启条件拒绝 | 用户被闸门逼急了，随手写"否决"把好想法毙掉。闸门保证有终态，不保证终态是对的 |

**闸门 1 的链条怎么成立**：`commit` 强制要求 `--seed-id`，且该 ID 必须存在于当天的 session 文件里。所以第二段只能展开第一段登记过的种子——这同时把 F1 的"第二段只处理用户点选的种子"变成了硬约束，而不是一句劝。这是本设计里性价比最高的一处：一个小脚本，把两条文本规则变成了真闸门。

**能拦 vs 只能劝的总账**：F5 的两个数量上限、F3 的字段形式、F4 的终态取值——真拦得住。F2 的假说质量、查新是否真做、AI 是否愿意调用脚本——只能劝。别把后三样当成已解决。

## 4. 数据安全设计

BRIEF 的头号风险是写坏迁移地图。`ib_map.py` 的每一次写入都走死同一条路径，没有第二条：

```
1. 读原文件 → json.loads
     解析失败 → 立即中止，退出码 4，原文件一个字节都不动
2. 记录 before_count = len(cells)
3. 备份：shutil.copy2 到 ~/.idea-bomb/backups/migration_map.<YYYYMMDD-HHMMSS>.json
     备份失败（磁盘满、权限） → 中止，退出码 4，不进入写入
     备份体积校验：备份文件大小必须 == 原文件大小，否则中止
4. 在内存里改数据
5. 写临时文件 ~/.idea-bomb/migration_map.json.tmp-<pid>
     write → flush → os.fsync(fd) → close
6. 回读校验：重新 json.load 临时文件
     解析失败，或 len(cells) != 预期值 → 删临时文件、中止、退出码 4
7. os.replace(tmp, target)   ← 同目录内 rename，POSIX 原子，不存在半截文件
8. 重算 sha256 写入 _integrity（作为第 7 步之后的下一次写入的基准）
```

几个刻意的选择：

- **备份放 `~/.idea-bomb/backups/` 子目录**，不跟用户手工建的那 5 个 `.bak*` 混在主目录。理由：一眼能分清哪些是脚本产的、哪些是你自己建的。
- **绝不自动删除任何备份**。轮转清理听起来整洁，但那是脚本删用户文件，触红线。改成 `status` 里提示一句"备份已 N 份、占 X MB，可手动清"。
- **os.replace 而不是 shutil.move**：前者在同一文件系统内保证原子语义，后者跨设备时会退化成拷贝+删除，中途断电就是半截文件。
- **回读校验对比 cells 数量**：这是最便宜也最有效的一道防线。序列化过程中任何导致条目丢失的 bug，在这里必炸，而且炸在原文件被替换之前。

## 5. 老数据兼容

103 个老格子在严格新规则下 **103/103 全部失败**（实测：每一格都至少缺 `feasibility_layers`/`falsification`/`diff` 之一）。所以兼容不是"尽量兼容"，是设计的前提。

### 5.1 核心机制：门禁只校验本次写入的那一格，从不校验全库

- `commit` 只校验 stdin 传进来的新 cell，不遍历老格子。
- `gate` / `status` 遍历全库，但**只看一件事**：`user_verdict` 是不是占位词。不看任何新增必填字段。
- 新格子打标 `"schema": 2`。老格子没有 `schema` 字段 → 视为 schema 1 → 永远不进新规则的校验路径。

结论：103 个老格子在新门禁下永远不会被判失败，因为它们根本不进校验。

### 5.2 分诊路径完全豁免新字段

F6 的 `verdict` 子命令改的是 schema-1 老格子。它**只校验两件事**：裁决值是不是三终态之一、归档有没有带重启条件。**不校验任何新必填字段**。否则 87 个老格子一个都补不动，分诊直接死掉。

### 5.3 已有真实裁决的 16 格不重新裁决

未裁决的判定用**黑名单**（占位词），不用白名单（三终态）。所以 `不建议作主课题`、`已否决（2026-09-15）：…`、`建议立即纳入工作流` 这 16 条算作已裁决，分诊不碰、零积压闸不报。

写入时反过来用**白名单**（只收三终态）。一松一紧是故意的：放行历史、收紧未来。

### 5.4 不做的兼容动作

- **不回填 `id` 字段**。cells 是只追加的，数组下标天然稳定；给 103 格统统加 id 要一次性改写全库，风险换不来收益。寻址改用 `下标 + idea 前 12 字校验`，对不上就拒绝写入，防错位。
- **不把归档格子搬到别的数组**。`user_verdict="归档"` + `archived=true` 原地打标，"活跃区"是过滤出来的视图。搬家会打乱下标、制造第二个存储、而且不可逆。
- **`rejected_or_downgraded` 数组冻结**。它现在有 1 条。不再往里写（新的否决一律走 cells 内的 `user_verdict="否决"`），也不删。理由：两个写者正是 BRIEF 明令要避免的。
- **不校验 `novelty` / `feasibility` / `quadrant` 的取值**。真实数据里它们是自由文本：`中-高`、`中高`、`甜区（创新中-高×可行高）`、`高但无意义`。强枚举会把你自己的自然写法判成非法，结果就是你绕开脚本。只查非空。
- **不校验 `feasibility_layers` 的键名**。真实数据里键名有 `biology`/`机制`/`delivery_signal`/`safety_executability`/`measure`/`caveat`，30 多种。只查"是 dict、≥3 个键、每个值非空"。

## 6. 风险评估

本项目动用户核心数据，按 rules.md 要求列 ≥2 个失败模式。实列 5 个。

### 风险 1：写坏迁移地图，103 格一次损毁（头号）

- **失败模式**：脚本序列化时丢字段/丢条目，或写到一半崩溃，留下半截 JSON。
- **缓解**：第 4 节的七步写入路径。三道独立防线——写前备份、临时文件回读校验（含 cells 数量比对）、os.replace 原子替换。任何一步失败原文件都保持原状。
- **残余**：极端情况下备份和原文件同时损坏（磁盘故障）。用户已有 5 个历史备份 + BRIEF 记录的回退点，可接受。

### 风险 2：门禁太严，AI 改为直接编辑 JSON 绕过（最阴险）

- **失败模式**：commit 被拒几次后，执行技能的 AI "聪明地"改用 Edit 工具写 JSON，从此所有闸门形同虚设——而且**比没有闸门更糟**，因为你会以为闸门在工作。
- **缓解**：① `_integrity` 的 sha256 校验，下次任何脚本运行时在 stderr 报警，把隐形绕过变成可见绕过；② 门禁的最小长度/条件规则全部按真实数据标定，不设不合理的严苛项，降低绕过动机；③ SKILL.md 明写禁令并说明理由；④ 验收时故意触发一次拒绝，看 AI 的反应是补字段还是绕路。
- **残余**：拦不住，只能发现。这是诚实结论。

### 风险 3：F6 批量归档误伤（一次写 80+ 格）

- **失败模式**：AI 排序失准，把一个真金想法批量归档；或批量写入中途出错导致部分写入，库进入半新半旧状态。
- **缓解**：① 批量裁决是**全有或全无**——任一条校验失败则整批拒绝、一格不写；② 归档不是删除，格子留在库里、带重启条件，随时可翻案；③ 批量前必须把完整清单摆给用户一次性确认，脚本**没有任何自动裁决模式**，`user_verdict` 的值只能由调用方显式传入；④ 已有终态裁决的格子默认拒绝覆盖，要 `--allow-overwrite` 才动，防止分诊洗掉你那 16 条已有判断。

### 风险 4：零积压闸把技能锁死

- **失败模式**：闸门上线，87 格未裁决，任何产出都被拒，idea-bomb 当场不可用。
- **缓解**：① 分诊命令不受零积压闸约束；② 上线顺序写死：先跑 F6 分诊清存量，再启用零积压闸；③ `gate` 被拒时的输出直接给出未裁决清单和该跑的分诊命令，不让人卡在"被拒了但不知道干嘛"。

### 风险 5：日上限的跨午夜与时区问题

- **失败模式**：一轮工作跨过 0 点，被算成两天，3 个上限失效一次（那天能出 6 个）。
- **缓解**：不修。代价是偶尔多出 3 个想法，远小于引入"轮次状态机"的复杂度。记录在案，出现再说。

## 7. 不做什么（主动砍掉的）

| 砍掉的东西 | 理由 |
|---|---|
| 想法相似度去重闸门 | BRIEF 实测：103 个想法两两 Jaccard>0.28 的对数为 **0**。建了也永远不触发，纯死代码 |
| 集成 idea-evaluator 的五维评分 | 与现有"两轴"职责重叠（创新性/可行性已覆盖 Higher/Cheaper 等维度的实际决策需求），且那套是英文、计算机论文语境（venue fit、baseline、SOTA），搬到湿实验室要大改才不别扭。真要借的"三种裁决"思想，BRIEF F4 的 采纳/否决/归档 已经自己长出来了。**唯一值得抄的是 `fatal-flaws.md` 的 F10「没考虑失败情况」**——但 idea-bomb 的证伪点必填已经覆盖了它，不必再搬一套 |
| 给 103 个老格子回填 `id` | 一次性改写全库的风险换不来收益；cells 只追加，下标+前缀校验够用 |
| 把闸门阈值做成配置项 | 用不上的配置就是垃圾。3 和 8 写死为脚本常量，要改就改那一行，改完自己知道自己放宽了 |
| 自动轮转删除旧备份 | 脚本删用户文件，触红线。改成 status 里提示手动清 |
| pending / 待办队列 | 第二个存储 = 第二个写者 = BRIEF 明令禁止；而且它会变成新的积压池 |
| `novelty`/`feasibility`/`quadrant` 的枚举校验 | 真实数据是自由文本，强枚举会逼用户绕过脚本 |
| 假说 `design` 字段的长度上限 | "不出详细实验方案"用字数卡是错的方法——夹叙夹议的好文字会被误杀。留在文本规则里劝 |
| 定时/自动运行、标书正文、文献综述、新建独立 skill、落点强制轮换 | BRIEF《明确不做》已列 |
| 改 profile.md | BRIEF 待定项。按 BRIEF 的排序：先改流程，改完发散度仍不达标再回头补 profile。本次不动 |

## 8. 验收怎么做（对应 BRIEF 成功标准）

| BRIEF 标准 | 验收动作 |
|---|---|
| 完整跑通一轮且零积压 | 在**真实地图的临时副本**上：register 5 个种子 → commit 2 个假说带终态裁决 → `gate` 返回退出码 0 |
| 闸门真能拦住 | pytest 覆盖：第 9 个种子、当天第 4 个假说、缺 falsification、`user_verdict=待定`、归档无重启条件——全部断言退出码 2 + 错误码。**测试一律跑在 `--map` 指向的临时副本上，绝不碰真实文件** |
| 存量清完 | 分诊后 `status` 的 `undecided` == 0 |
| 盲测过关 | 新旧两版各跑一轮，去掉版本标记交用户盲选。选不出差别即本次改造失败 |

第 4 条是唯一真正检验 F2 的标准。前三条只证明闸门在工作，不证明想法变好了。
