# 06 发布（标准档；首次公开、建公开仓、发 Release 或包、第一次上线都在这里；已上线服务的修复部署在轻档卡点 B 确认）

目标：建 GitHub 仓库、写陌生人能上手的 README、走 PR + CI 合并发布。

## Step 1 ⏸ 卡点4：发布信息确认（先问再动）

问用户：

1. 仓库名（给建议名）。
2. 公开还是私有（公开仓 GitHub Actions 免费）。
3. 主分支名（默认 main）。
4. README 要补的内容（徽章、致谢、License）。
5. 发布形态：只推代码 / GitHub Pages / Release + tag / npm / PyPI。

这一个卡点覆盖后续所有 push、公开动作和新建 `.github/workflows/ci.yml`（rules.md 红线里的 CI 配置，这里一次授权），中途不再逐次问。只问会改变公开结果或需要授权的事，推荐明显占优的直接定，汇报里一句话列出来。

用户默认"该发了、公开"的，确认前给一条【反向拷问】（≤100 字）挑没验证的完成假设：核心流程真跑通了吗、公开还是私有的默认对不对、有没有为赶进度跳过的。用户已明确权衡过的不复读。

## Step 2：建仓库

```bash
gh repo create <名字> --private|--public --source=. --remote=origin
```

没装 gh 或没登录：把命令给用户自己跑，或引导 `gh auth login`。建完 `git remote -v`，本机用 SSH 别名的按 rules.md"GitHub 推送与网络"第 1 条改过去：`git remote set-url origin git@github.com-<账号>:<用户名>/<仓名>.git`。

**公开仓首次 push 前先清过程档案（选 `--public` 必做）**：`.devflow/`、`PROJECT.md`、`LEARNINGS.md` 是过程档案不是产品。此刻还没推送过，改写历史零风险、不用 force。按顺序：

1. 并行开发留下的 worktree 和模块分支先按 04-并行 E 节删掉。在 feature 分支上先暂存：`mkdir -p ../过程档案暂存 && cp -r .devflow PROJECT.md LEARNINGS.md ../过程档案暂存/ 2>/dev/null`。`git status --porcelain` 必须为空（filter-branch 要求工作区干净），不空的只许点名提交这三个路径，其他路径有改动先停下判断（缓存和测试产物不能进公开仓）。再 `git checkout <主分支名>`，本地主分支名和卡点 4 定的不一致先 `git branch -m <旧名> <主分支名>`。
2. 清洗（`--all` 把 feature 分支和 tag 一起改写）：
```bash
FILTER_BRANCH_SQUELCH_WARNING=1 git filter-branch --index-filter 'git rm -r --cached --ignore-unmatch .devflow PROJECT.md LEARNINGS.md' --prune-empty --tag-name-filter cat -- --all
cp -r ../过程档案暂存/. . && printf '\n.devflow/\nPROJECT.md\nLEARNINGS.md\n' >> .gitignore
git add .gitignore && git commit -m "chore: 过程档案本地化，不入公开仓"
git checkout feature/<功能名> && git merge --no-ff <主分支名>
```
.gitignore 冲突两侧的行全保留再提交，其他文件冲突停下报用户。重跑时 refs/original 已存在会被拒绝，加 `-f`；refs/original 留着带档案的旧历史，不许 `push --mirror`。
3. 核验，三条都过才往下，有一条不过保留暂存目录停下报告：`git log <主分支名> feature/<功能名> --oneline -- .devflow PROJECT.md LEARNINGS.md` 为空（别用 `--all`，refs/original 会误报）；`for p in .devflow PROJECT.md LEARNINGS.md; do git check-ignore -q "$p" || echo "没被忽略: $p"; done` 无输出；`diff -r ../过程档案暂存/.devflow .devflow && diff ../过程档案暂存/PROJECT.md PROJECT.md` 无差异。过了再删暂存目录（在卡点 4 授权范围内）。之后 README 和 ci.yml 都在 feature 分支上提交。
4. 改写历史后 commit hash 全变，锁作废，重新定位：`git log feature/<功能名> --format=%H --grep='^test: 验收测试锁定' -1 > .devflow/LOCK`，并更新 PROJECT.md 里记的值（否则下次验收核查报锁不在历史里）。
5. 先做 Step 5 第 1 条密钥终检，过了才 `git push -u origin <主分支名>`（远端有主分支，PR 才有合并目标）；push 后立即 `git remote set-head origin -a`，把 05.5 造的 origin/HEAD 替身换成真引用。

档案本地照留、照常续接，只是不进远端。私有仓不清（档案进 git 换来审计链、方案历史和换机续接）；私有转公开前同样清一次，但那时历史已推过，要改写历史加强推（rules.md 红线），且已合并的 PR 永久钉着旧内容清不掉，这两点先告知用户并经确认。

## Step 3：README（写给没看过代码的人）

必含：这是什么、能干什么、安装步骤（从零开始，含依赖）、部署步骤（如适用）、使用教程（带真实示例命令或截图位）、常见问题。写完自查：没参与开发的人照着能不能跑起来。

## Step 4：GitHub Actions

按项目类型生成最小 workflow（`.github/workflows/ci.yml`）：装依赖、lint/typecheck（项目有就跑）、单测 + 验收测试、依赖漏洞扫描（Node 用 `npm audit --audit-level=high`，Python 用 `pip-audit`）。网页项目跑测试前必须 `npx playwright install --with-deps`（CI 里没浏览器）。有构建步骤的项目加一步构建。BRIEF 有多平台要求的用矩阵跑对应系统（`runs-on` 按需选 ubuntu、windows、macos），05 标"待 CI"的用例在这里判定，红了回 04 修。不堆用不上的。

## Step 5：PR、合并、发布

1. 推送前密钥终检（一票否决）：`.env` 等敏感文件已被 `.gitignore` 排除、`git log -p` 抽查历史没混进 key、源码无硬编码凭证（push 出去就收不回）。
2. push feature 分支，建 PR，描述写清做了什么、测了什么。
3. 等 Actions 绿，红了回 04 修，不许绕过 CI 合并；缺系统库、缺浏览器这类环境问题先补 workflow 安装步骤，不计入打回轮次。
4. 合并进主分支，跑一次 `git remote set-head origin -a`（归正 05.5 造的替身）。
5. 按卡点 4 确认的形态发布：开 Pages / `gh release create` + tag / npm 或 PyPI publish。

## 完成标准

卡点 4 确认的发布动作全部完成、CI 绿、README 在线可读，进 07。
