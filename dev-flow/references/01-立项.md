# 01 立项（只有新项目进这里；写完 BRIEF 后按分级：只本地用走中档，要发布走标准档）

目标：把一句模糊的想法变成没有歧义的需求定稿 BRIEF.md。

## Step 0：确认工作文件夹（先于一切）

问用户项目做在哪：当前会话所在文件夹，还是新建一个（问清路径和名字）。路径确认前不创建任何文件。

## Step 1：grilling 拷问（按档裁剪）

调用 `grilling` 技能逐个问题拷问，覆盖：

- 动机：解决什么真实问题，已有现成工具为什么不用。
- 用户和场景：谁用、什么场景、多久用一次。
- 核心功能：最小可用版本必须有什么，每个功能能不能说成"输入 X 得到 Y"。
- 边界：明确不做什么（不写下来的边界日后都会扯皮）。
- 成功标准：做到什么程度算做完，怎么验证。
- 项目类型：代码/脚本、网页/前端、skill/prompt，还是混合。
- 平台范围：只跑 Mac，还是兼容 Windows、Linux，网页兼容哪些浏览器（决定测试策略）。
- 技术偏好：有指定语言、框架、库吗，没有留给方案阶段调研。
- 数据与依赖：需要外部 API、数据库、登录态吗。
- 敏感面（三问必答，05.5 按它核对有没有越权）：程序碰哪些用户文件、数据，读写删范围各是什么；要不要密钥、登录态，存哪；往哪些外部地址发数据。
- 发布意图：上不上 GitHub，公开还是私有，要不要部署上线。

只本地用（中档）的问清动机、功能清单、边界、敏感面四项就停，一轮为限；要发布（标准档）的拷问到每个功能都能写成"输入 X 得到 Y"，边界、成功标准、平台范围全部落字。用现成技能产出内容、纯写作不是开发任务，不进本流程。

## Step 1.5：反向拷问（仅当用户自带方案或强主张）

用户自带解决方案或强主张（"做个 X 用 Y""必须自己写""一定要上线"）的，进方案前给一条【反向拷问】（≤100 字）挑没验证的前提、盲点或更短的路径（现成工具能不能直接解决、是不是伪需求、最小版本能不能再砍）。用户坚持就照走，风险记进 BRIEF。只是来问能不能做、怎么做的跳过。

## Step 2：定测试策略

按项目类型和平台范围写明测试怎么做，进 BRIEF.md：

| 类型 | 验收测试形态 |
|---|---|
| 代码/脚本 | pytest / node test 调用对外接口（CLI 命令、函数），真实跑 |
| 网页/前端 | 起本地服务 + 浏览器自动化走真实用户流程 |
| skill/prompt | 测试 prompt 清单 + 产出评分标准，裁判盲测实际产出 |
| 多平台要求 | 立项时定哪些平台必测、哪些平台"尽力而为"，写死进 BRIEF |

## Step 3：初始化

1. `git init` 加合适的 `.gitignore`。
2. 建 `.devflow/`，写 `BRIEF.md`：背景与动机 / 功能清单（每条"输入 X 得到 Y"）/ 不做的事 / 成功标准 / 项目类型与平台范围 / 测试策略 / 敏感面声明 / 发布意图。
3. 项目根建 `PROJECT.md` 状态账本（格式见 04-并行worktree.md 末节，只有主会话写），登记初始待办。
4. 首次 commit：`chore: 立项，需求定稿`。

## 完成标准

BRIEF.md 落盘且用户对拷问结论无异议，进 02。
