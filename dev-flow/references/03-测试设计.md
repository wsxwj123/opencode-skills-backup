# 03 测试设计（只有标准档走这里；轻档、中档用轻档.md 里的限量测试代理）

目标：在写第一行实现代码之前，由独立代理站在用户角度写好验收测试并锁定。

为什么这么严：让 AI 看着自己写的代码出测试，等于学生自己出考卷自己判卷，测试会不自觉迁就实现，代码错了测试跟着错。调研证据（AgentCoder、SpecBench 等）一边倒：写测试的不许看实现。

## Step 1：测试设计代理（opus，独立子代理）

给它的输入只有：`.devflow/BRIEF.md` + `.devflow/INTERFACE.md`（02 单独抽出的接口约定），外加 snippets 预算块。不给 PLAN.md，里面的文件结构和任务拆解是实现思路，看了黑盒就破功。

Prompt 里明确写："只依据我给你的这两个文件（BRIEF.md、INTERFACE.md）设计测试；除这两个文件外，不得查看 `.devflow/` 下任何其他产物（PLAN.md、RESEARCH-*、代码地图都是实现思路，看了黑盒就破功），不得查看项目源码和 git 历史。站在真实用户的角度设计测试。"

要求覆盖（缺哪类要说明为什么不适用）：

1. **正常路径**：BRIEF 里每条"输入X→得到Y"的主路径，典型输入→预期输出。
2. **边界**：0、1、空、负、极大极小、临界值、单元素、超长、Unicode/特殊字符。
3. **错误路径（最易漏，重点）**：乱输入、空输入、缺参、类型错、重复操作、误操作、文件缺失、断网、越权、依赖不可用，必须被正确拒绝或妥善处理，不能崩、不能静默出错；每种断言"具体的"失败行为（确切的退出码/异常类型/报错文案），不是笼统"会报错"。
4. **反向用例**：不该发生的事断言它没发生（不该写库的没写、不该返回的没返回、不该删的文件还在）。
5. **幂等/并发**（若适用）：重复调用、并发调用、重复运行不产生脏数据。
6. **用户没想到的也要想到**：需求没明说但按常理必须正确的行为（中文文件名、路径带空格等），按 BRIEF 定的平台范围顾兼容性。

每个测试只测一件事，命名说清场景；断言要具体（确切值/异常/退出码，别只断言非空/不报错）；测试间不许有依赖、能任意顺序跑；不引入没必要的框架和 fixture。交付时明说覆盖了什么、没覆盖什么，不假装全覆盖。

**规模预算**：默认总数不超过 30 条，按对外入口和风险分配，超出要在 TEST-PLAN 里写明理由；默认只派 1 个代理，多个互不相关的子系统才分组。一个项目 4 组代理写了 717 条、冒出 46 处"接口没写清"要逐条澄清，这就是不限规模的代价。派的时候带 snippets 预算块（测试设计档位）。

## Step 2：产出（按项目类型分叉）

| 类型 | tests/acceptance/ 里放什么 |
|---|---|
| 代码/脚本 | 可执行测试（pytest / node test），只通过对外接口调用（CLI、公开函数），不 import 内部模块 |
| 网页/前端 | **`@playwright/test` 的 spec 测试文件**（npm 标准测试框架，带断言/报告，`npx playwright test` 可复跑、可进 CI）走真实用户流程：打开页面→操作→断言看到的结果。注意：playwright **MCP** 和 agent-browser 是交互式驱动工具，产不出可提交复跑的测试文件，**不能当验收测试产物**（它们的定位是 04 开发期探路调试） |
| skill/prompt | 测试 prompt 清单 + 每条的产出评分标准（什么样算合格），供 05 裁判盲测 |

同时产出 `.devflow/TEST-PLAN.md`（人话版清单）：每条一行，场景 / 怎么操作 / 预期看到什么。这是给用户看的。

## Step 3：守卫检查（主会话执行）

先跑一次 `pytest --collect-only tests/acceptance`（或测试框架的等价命令）确认用例都能被收集，收集不了的打回；从零开始的项目还没有实现代码，测试设计代理可以按 INTERFACE 加接口桩（只有签名，函数体 `raise NotImplementedError`），收集得过就行。然后检查验收测试内容：不得出现 INTERFACE.md 之外的实现细节（内部函数名、私有模块、数据库表名等）。出现 = 黑盒破功，打回 Step 1 重写。打回时新开代理，打回意见只说"第 X 条出现了 INTERFACE 之外的细节"，不复述具体是哪个内部名（复述本身就是二次泄露）。

## Step 4 ⏸ 卡点2：清单锁定

把 TEST-PLAN.md 给用户过目（说人话）：一共多少条、覆盖哪些方向、哪几条是"替你想到的"。用户可增删。

确认后锁定，hash 必须落盘（05 从文件读，不靠会话记忆，防长会话遗忘）：

```bash
git add tests/acceptance .devflow/TEST-PLAN.md <接口桩文件> && git commit -m "test: 验收测试锁定"
git rev-parse HEAD > .devflow/LOCK
shasum -a 256 .devflow/BRIEF.md .devflow/INTERFACE.md .devflow/TEST-PLAN.md > .devflow/LOCK.sha   # 判据文件指纹：公开仓清洗后这些文件不再被 git 跟踪，05 靠它核对
echo "标准档锁定 $(cat .devflow/LOCK)" >> PROJECT.md
git add .devflow/LOCK .devflow/LOCK.sha PROJECT.md && git commit -m "chore: 记录验收测试锁定 hash"   # 公开仓已 ignore 这些路径时 git add 会报错，跳过这次提交，文件留本地即可
```

锁的真值永远能从 git 推回来：`git log --grep='^test: 验收测试锁定' --format=%H -1`，文件和账本只是副本，05 Step 1 三者比对。此后开发代理对 `tests/acceptance/` 只读。

锁定后发现测试本身有夹具或时序问题：仍然新派一个测试设计代理（只给 BRIEF + INTERFACE + 失败现象），主会话核查的 diff 范围包括夹具和数据文件，改完重新执行上面的锁定命令。不许开发代理改，也不许续用原来的测试代理：开发期一句"是夹具问题"、把输入数据换掉就变绿，这是测试迁就实现的后门。

## 修 bug

修 bug 默认走轻档.md，复现测试由那里的限量测试代理写。只有标准档的 bug（命中分级表标准档那一行：动数据结构、删除路径、批量改写这类）才到这里：核心产物是复现测试，修之前跑必须失败、修之后必须通过，另加 1–2 条相邻场景的回归用例，同样锁定后进 04。
