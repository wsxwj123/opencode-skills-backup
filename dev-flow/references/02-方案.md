# 02 方案

目标：产出一份经过独立盲审的方案定稿。出方案和挑毛病必须是两个独立的子代理。修 bug 不在这里，走 [轻档.md](轻档.md)。

## 中档走法

1. 主会话按轻档.md Step 0 写 `.devflow/<任务名>.md`（现象或需求 / 根因或影响面 / 对外行为变化 / 错误契约 / 敏感面 / 行为清单）。新项目只本地用的，先走 01 写 BRIEF。
2. 派一个方案代理（命名 `planner`，带预算块·调研+方案），调研、方案、最小实验由它一个人做。只有新技术选型或冷门需求才调研。产出写进任务文件的"方案"一节：架构与选型、文件改动、接口变化、任务拆解、风险。
3. 派一个盲审代理（新开，带预算块·方案盲审），输入只有任务文件。Prompt 照抄："这是隔壁同事做的方案，你详细审查一下。只依据我给你的这一个文件判断；除它之外不得查看 `.devflow/` 下任何其他产物、不得查看 git 历史、不得查看实现代码。"按 Step 3 的三级和四维度审，致命、重要必须处理。
4. 修订：续用 `planner` 改，主会话对着审查意见逐条核对。只有致命问题没解决才开第二轮盲审（新开代理），用户在卡点推翻审查意见不算。定稿后主会话按接口变化回改行为清单。
5. ⏸ 卡点 1：照 Step 5 汇报，用户看的是任务文件的"方案"一节，并确认行为清单。确认后按分级表重判一次档，然后开 `feature/<任务名>` 分支，PROJECT.md 记"卡点1已确认"，把对外行为变化 / 错误契约 / 行为清单抽成 `<任务名>-接口.md`，跳过轻档的 Step 0 和卡点 A，从轻档 Step 1 派测试代理（中档档位，测试上限 25）。
6. 命中参数直接拼进 SQL/命令/路径或动已有登录/密钥/权限代码的，轻档验收通过后按轻档"安全"节派审计代理。

输入：`.devflow/BRIEF.md`（没有就先按 01 补一份简版）。

## Step 0：已有项目加功能，先补一轮需求拷问（新项目跳过）

针对本次新增或变更做一轮 grilling（同 01 Step 1，只聚焦这次）：解决什么、输入什么得到什么、边界、成功标准、会不会碰新的数据或权限。用户带着明确做法来的，补一条【反向拷问】。结论并进 BRIEF.md。

## Step 1：调研（有需要才做）

先判断需要哪些调研：技术选型、官方文档用法、现成轮子、平台限制。

- 每个主题派一个独立调研代理（带预算块），可并行；搬现成代码、照已定接口实现的不派。
- 优先查官方文档和源头资料，产出 `.devflow/RESEARCH-<主题>.md`，含结论、依据、来源链接。
- 已有项目首次进流程必产代码地图 `.devflow/RESEARCH-代码地图.md`：目录结构、关键模块与职责、代码风格、可复用的工具函数和类型、测试怎么跑。此后方案、开发、修复代理都带上它；盲审、裁判、测试设计代理不发（用不上，少一个泄露面）。地图只记现状，出现本次功能名或"建议改成"这类方案倾向就打回重写；明显落后于当前代码的先增量刷新。
- 可能有现成 skill 时用 `find-skills` 查，装不装问用户。
- 没有现成轮子的冷门需求，派调研代理查社区已有实现（开源项目、技术文章、issue），协议允许就 clone 到本地读源码，结论回答"业界常规做法是什么、踩过什么坑"。跳过这步，方案代理容易凭空设计出高危路径（改系统组件、hook 他人进程、绕过平台安全机制）。
- 方案必须基于调研写，不凭记忆猜 API 用法。
- "到底行不行"的假设必须用最小实验验证：方案依赖某个无法靠文档确定、在目标环境能不能跑的假设，就写一个最小可运行 spike 真跑一遍，再定方案。

## Step 2：方案代理（opus，独立子代理）

输入：BRIEF.md + 所有 RESEARCH 文件（含代码地图）+ rules.md + 预算块（调研+方案）。命名 `planner`，Step 4 修订续用。

产出 `.devflow/PLAN.md`，必须包含：

1. 架构与技术选型（附理由，引用调研结论）
2. 文件结构
3. 对外接口约定：CLI 命令及参数 / 页面 URL 与操作入口 / 公开函数签名 / skill 调用方式，写到不看实现也能照着写测试的程度，每个入口必须写明错误契约（非法输入返回什么：退出码、异常类型、报错文案）。单独存一份 `.devflow/INTERFACE.md`，测试设计代理只拿这一份。
4. 任务拆解（按模块，标注顺序依赖，互不依赖的标"可并行"）
5. 风险清单（按 rules.md：每个非机械改动至少 1 个失败模式加缓解；BRIEF 敏感面的每一项配一句怎么保证不越权、不泄露）

## Step 3：审查代理（独立子代理，盲审）

Prompt 开头照抄："这是隔壁同事做的方案，你详细审查一下。只依据我给你的这三个文件（BRIEF.md、PLAN.md、INTERFACE.md）判断；除这三个文件外，不得查看 .devflow/ 下任何其他产物、不得查看 git 历史、不得查看实现代码。"不透露方案出自另一个 AI 或本会话。

输入：BRIEF.md + PLAN.md + INTERFACE.md + 预算块（方案盲审）。要求：

- 按致命 / 重要 / 建议三级列出，每条给位置、为什么是问题、怎么改，先说最要命的。
- 重点：需求覆盖缺漏、架构隔离、接口约定含糊、被低估的风险、过度设计。
- 必查：INTERFACE.md 的错误契约是否每个入口都写清，且与 PLAN 第 3 节一致，缺了判"重要"。
- 必查：方案是否依赖未经最小实验验证、又无法靠文档确定的假设，有就判"重要"，打回补实验。
- 四维度逐个过（只查方案层，不查代码）：
  1. 正确性：错误契约完整、边界场景（空/0/超长/并发/重复操作）、状态与数据流有没有漏态。
  2. 安全：BRIEF 敏感面每一项有没有对应保障、信任边界、注入面和密钥暴露；实现路径是否高危（改系统组件、hook 他人进程、绕过平台安全机制、写项目外目录），有常规做法却没走的判"重要"以上。
  3. 性能：架构层面的明显低效（注定 N+1、全量扫描）。
  4. 可维护性：过度设计和抽象不足都查。过度设计＝单实现的抽象、用不上的配置、为想象需求预留的扩展点；抽象不足＝同类问题靠枚举、硬编码分支、白名单逐条堆，没有统一机制。判据是集合开不开放：有限封闭（星期、HTTP 方法）可以枚举，开放会新增（用户输入格式、第三方页面结构、文件类型、错误码）必须抽机制。另查模块拆分。
- 架构改动重的，可再派一个架构审查代理（同样盲审），专挑模块边界、依赖方向、循环依赖、设计模式硬套、可演进性。
- "没发现致命问题"也是合格产出，不许硬凑。

## Step 4：修订

审查意见回传 `planner` 续用修订（致命、重要必须处理，建议可说明不采纳理由），主会话对着审查文件逐条核对是否处理完。只有致命问题没解决才走第二轮 Step 3，用户在卡点推翻审查意见不算；二轮必须新开审查代理（续用的审查员只核对自己的意见，不挑修订版的新毛病）。

## Step 5 ⏸ 卡点1：方案定稿

向用户汇报：方案做什么、怎么做、审查挑出什么、怎么改的、还剩什么风险。提问不超过 4 项，只问会改变用户看得见的结果或需要授权的事；推荐明显占优的直接定；选项用用户能懂的词；修法先给最简单的办法，没实测的代价不写成定论。

必须让用户看到方案本身：plan 模式下用对应 agent 的计划卡片（Claude Code 用 ExitPlanMode）；其他模式提醒用户查看 `.devflow/PLAN.md`，不只口头概括。

用户推翻审查关键意见或坚持某个审查没覆盖的选择时，给一条【反向拷问】（≤100 字）；被动确认的不拷问。

用户确认后 PLAN.md 定稿，commit `docs: 方案定稿`，进入 03。

## 修 bug

默认走 [轻档.md](轻档.md)。根因在架构上、要改接口契约、要动登录/密钥/权限代码的回中档走法；碰数据结构或删除路径的走标准档。
