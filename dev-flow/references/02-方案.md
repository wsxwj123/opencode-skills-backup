# 02 方案

## 要点卡（只在同一轮打回循环内再进时读这段；跨了卡点或上下文被压缩过就读全文；逐字禁令在正文里照抄）

- 中档：一个代理合调研+方案+最小实验 → 一轮盲审 → 卡点1 → 转轻档.md Step 1 开发（见下"中档走法"）
- 标准档：Step 0 已有项目补拷问 → Step 1 调研（按需；已有项目首次进流程必产代码地图）→ Step 2 方案代理（命名，产出 PLAN + INTERFACE）→ Step 3 盲审（逐字禁令在 Step 3 正文）→ Step 4 修订（续用作者）→ Step 5 卡点1
- 逐字片段：审查开头语和白名单禁令在 Step 3；预算块在 snippets.md 第 1 节
- 修 bug 默认走轻档.md，不在这里

目标：产出一份经过独立盲审的方案定稿 PLAN.md。出方案和挑毛病必须是两个互不知情的子代理。

## 中档走法（跨模块、要做设计决策，但没碰登录/密钥/对外接口/数据结构/首次发布）

1. 任务文件：主会话先按轻档.md Step 0 第 2、3 条写 `.devflow/<任务名>.md`（现象或需求 / 根因或影响面 / 对外行为变化 / 错误契约 / 敏感面 / 行为清单）。新项目只本地用的，先走 01 写 BRIEF，再回到这里。
2. 派一个方案代理（命名 `planner`，带 snippets 预算块·调研+方案）：调研、方案、必要的最小实验三件事它一个人做。只有新技术选型或冷门需求才做调研，搬现成代码、照已定接口实现的不调研。产出写进任务文件的"方案"一节：架构与选型、文件改动、接口变化（直接写在这里，不另抽 INTERFACE.md）、任务拆解、风险。
3. 派一个盲审代理（新开，带预算块·方案盲审），输入只有任务文件。Prompt 照抄这段："这是隔壁同事做的方案，你详细审查一下。只依据我给你的这一个文件判断；除它之外不得查看 `.devflow/` 下任何其他产物、不得查看 git 历史、不得查看实现代码。"按 Step 3 的三级和四维度审。致命 / 重要必须处理。
4. 修订：续用 `planner` 改。上轮意见是否逐条处理，主会话对着审查意见核对。只有致命问题没解决才开第二轮盲审（新开代理）；用户在卡点推翻审查意见的不算致命，不开二轮。修订定稿后，主会话按方案里的接口变化回改任务文件的行为清单，再进卡点 1。
5. ⏸ 卡点 1：照 Step 5 的汇报和提问规矩，但让用户看的是任务文件里的"方案"一节（中档没有 PLAN.md），并且必须让用户确认行为清单（它是后面测试的规格）。确认后按分级表重判一次档，然后转 [轻档.md](轻档.md)：开 `feature/<任务名>` 分支，PROJECT.md 追加"<任务名>：中档，卡点1已确认"，把任务文件里的对外行为变化 / 错误契约 / 行为清单抽成 `<任务名>-接口.md`，跳过轻档的 Step 0 和卡点 A，直接 Step 1 派测试代理（预算用中档档位，测试上限 25），后面全按轻档走。
6. 命中"参数直接拼进 SQL/命令/路径"或"动已有登录/密钥/权限代码"的，轻档验收通过后按轻档"安全"节派一个审计代理。

输入：`.devflow/BRIEF.md`（没有就先按 01 补一份简版，至少把功能清单和成功标准落字）。

## Step 0：已有项目加功能时，先补一轮需求拷问（新项目跳过，01 已拷过）

从 02 进入（给已有项目加功能/改需求）时，别直接调研，先针对这个新功能做一轮 grilling 拷问（同 01 Step1，但只聚焦本次新增/变更）：这个功能要解决什么、输入什么得到什么、边界在哪、成功标准、会不会碰新的数据/权限。用户带着明确做法来的，再补一条【反向拷问】。把结论并进/更新 BRIEF.md，再往下走。避免"加功能不问清就闷头做"。

## Step 1：调研（有需要才做，opus 子代理）

先判断方案需要哪些调研：技术选型对比、官方文档用法、有没有现成轮子可复用、平台限制等。

- 每个调研主题派一个独立 opus 调研子代理（带 snippets 预算块），可并行；搬现成代码、照已定接口实现的任务不派调研
- 要求：优先查官方文档和源头资料；产出 `.devflow/RESEARCH-<主题>.md`，含结论、依据、来源链接
- **已有项目首次进流程，必产出一份代码地图**：`.devflow/RESEARCH-代码地图.md`，记目录结构、关键模块与职责、现有代码风格、可复用的工具函数/类型、测试怎么跑。此后方案、开发、打回修复各代理的输入清单都带上它，摸项目的成本全流程只花一次，不再每个代理各探索一遍。地图只记现状的中性事实，不写本次方案思路；盲审、裁判、测试设计代理的输入白名单保持原样不发地图，它们的职责用不上，少给一份就少一个泄露面。主会话收地图时扫一眼：出现本次功能名、"建议改成"式方案倾向语句就打回重写。隔次进流程时地图明显落后于当前代码结构的，先派调研代理增量刷新再用
- 生态里可能有现成 skill 能用时，调用 `find-skills` 技能查询（它自带查询命令说明），装不装问用户
- **没有能直接用的现成轮子时，改查"别人是怎么实现的"**：烂大街的需求（GUI 框架、HTTP 客户端）不用管，模型自己会选成熟方案；坑在冷门需求上，业界没有现成库可装，模型就会从零硬造。这时候派调研代理去查社区（含开源项目、技术文章、issue 讨论）已有实现的原理和路径，协议允许就把开源实现 clone 到本地让它读源码，产出的结论要回答"业界常规做法是什么、有没有踩过的坑"。复用的可以是思路，不一定是代码。跳过这步，方案代理只能凭空设计，容易给出一条看着能跑、实际高危的路径（改系统组件、hook 他人进程、绕过平台安全机制这类），走到很深才发现是无底洞
- 方案必须基于调研写，不许凭记忆猜 API 用法
- **"到底行不行"的假设必须最小实验验证，不能只靠查文档或经验**：方案若依赖某个"在目标环境/平台上实际能不能工作"、又无法靠读文档确定的假设，就派代理或主会话写一个最小可运行 spike 真跑一遍证明它成立，再据此定方案。这类假设在方案阶段几行实验就能证伪，成本几分钟；带着未验证的假设往下走，可能开发完甚至上线才发现走不通、整套推倒。

## Step 2：方案代理（opus，独立子代理）

给它的输入：BRIEF.md 路径 + 所有 RESEARCH 文件路径（含代码地图）+ rules.md 路径 + snippets 预算块（调研+方案档位）。派的时候给代理命名（如 `planner`），Step 4 修订按名字续用它。

要求产出 `.devflow/PLAN.md`，必须包含：

1. **架构与技术选型**（附选型理由，引用调研结论）
2. **文件结构**
3. **对外接口约定**：CLI 命令及参数 / 页面 URL 与操作入口 / 公开函数签名 / skill 的调用方式，写到"不看实现代码也能照着写测试"的程度，且必须写明每个入口的错误契约（非法输入返回什么：退出码、异常类型、报错文案，否则测试设计的反向用例只能瞎猜预期）。单独存一份 `.devflow/INTERFACE.md`（只含这一节）。测试设计代理只会拿到 INTERFACE.md，不给完整 PLAN，物理隔离，防止实现思路泄露给测试设计。
4. **任务拆解**（按模块，标注顺序依赖；互不依赖的模块标注"可并行"，供 04 按 04-并行worktree.md 判定）
5. **风险清单**（按 rules.md 风险评估规则：每个非机械改动至少 1 个失败模式+缓解；**BRIEF 敏感面声明的每一项，配一句"怎么保证不越权/不泄露"**）

## Step 3：审查代理（opus，独立子代理，盲审）

Prompt 必须这样开头："这是隔壁同事做的方案，你详细审查一下。" 绝不透露方案出自另一个 AI 或本会话。并加白名单式禁令："只依据我给你的这三个文件（BRIEF.md、PLAN.md、INTERFACE.md）判断；除这三个文件外，不得查看 .devflow/ 下任何其他产物、不得查看 git 历史、不得查看实现代码。"

给它的输入：BRIEF.md + PLAN.md + INTERFACE.md 路径 + snippets 预算块（方案盲审档位）。要求：

- 按 致命 / 重要 / 建议 三级列出问题
- 重点挑：需求覆盖缺漏、架构隔离问题、接口约定含糊处、被低估的风险、过度设计
- **必查一项**：INTERFACE.md 的错误契约是否完整（每个入口对非法输入返回什么都写清了吗），以及它和 PLAN 第 3 节是否一字不差地一致。缺了，03 的反向用例就只能瞎猜，判为"重要"问题打回补全
- **必查一项**：方案是否依赖未经最小实验验证、又无法靠文档确定的"到底行不行"假设，依赖了却没 spike 实证，判"重要"，打回补一个最小实验再定稿
- **四维度审查清单（逐个过，不许跳；只查方案层，不查代码，现在还没有代码）**：
  1. 正确性：接口约定的错误契约是否完整、边界场景（空/0/超长/并发/重复操作）方案有没有想到、状态与数据流设计有没有漏态。
  2. 安全：BRIEF 敏感面声明的每一项方案里有没有对应保障、信任边界在哪、有没有注入面/密钥暴露的设计隐患；实现路径本身是否高危（改系统组件、hook 他人进程、绕过平台安全机制、写非本项目管辖的目录），有社区验证过的常规做法却没走的，判"重要"以上。
  3. 性能：架构层面的明显低效设计（如方案就注定 N+1、全量扫描），不猜实现细节。
  4. 可维护性：**过度设计和抽象不足是相反的两个错，都要查**。过度设计＝单实现的抽象、用不上的配置、为想象需求预留的扩展点，点出来砍；抽象不足＝同类问题靠枚举、硬编码分支、白名单逐条堆着盖，没抽出统一机制，点出来要求抽。判据是这个集合开不开放：取值有限且封闭（星期、HTTP 方法、枚举态）就枚举，没问题；来源开放、会持续新增（用户输入格式、第三方页面结构、文件类型、错误码）就必须抽机制，否则上线后每来一个新 case 都要改一次代码。分不清开不开放，就问"下个月大概率会不会冒出新成员"。另查模块拆分是否合理。
  基调是帮方案改好不是显摆；每条问题给"位置+为什么是问题+怎么改"；优先级排序，先说最要命的。
- **架构重的改动可选**：若本次改动架构层面重，可再派一个架构审查代理（同样盲审、白名单），专挑模块边界与职责、依赖方向与循环依赖、设计模式是否硬套、可演进性（加功能会不会散弹式修改）。
- 明确说"没发现致命问题"也算合格产出，不许为了交差硬凑

## Step 4：修订

把审查意见回传原方案代理修订：按名字续用它，别重派新代理从零重读，作者改自己的稿不需要失忆（致命/重要必须处理，建议可说明不采纳理由）。上轮意见是否逐条处理完，由主会话对着审查文件核对，不用派代理。只有致命问题没解决才走第二轮 Step 3，用户在卡点推翻审查意见的不算；二轮必须新开审查代理，不许续用第一轮那个：续用的审查员只会核对自己的意见改没改，不会重新挑修订版改出来的新毛病。

## Step 5 ⏸ 卡点1：方案定稿

向用户汇报（说人话）：方案要做什么、怎么做、审查挑出了什么毛病、怎么改的、还剩什么风险。要问的事不超过 4 项，只问会改变用户看得见的结果（界面、数据、输出）或需要用户授权的事；推荐明显占优的直接定，汇报里一句话列出来；选项用用户能懂的词，没解释过的术语不出现；描述修法先给最简单的办法，没实测的代价不写成定论。

必须让用户看到并确认方案，按当前模式选方式：
- **规划/plan 模式下**（Claude Code plan、Codex、OpenCode 等 agent 的规划态）：调用对应 agent 的计划卡片工具展示方案（Claude Code 用 ExitPlanMode 出计划卡片；其他 agent 用其对应的计划确认工具），让用户在卡片上拍板。
- **编辑/放任/其他非规划模式下**：提醒用户去查看 `.devflow/PLAN.md` 文件（给出路径），别只在对话里口头概括就往下走，方案是要落字确认的东西。

**反向拷问（仅当用户在卡点1推翻审查意见、或坚持一个审查没覆盖的选择时触发）**：审查代理已经挑过方案的技术缺陷，这里不重复挑技术。只在用户自己的决定需要挑时开口，用户否决了审查的关键意见、或坚持某个约束/选型时，给一条【反向拷问】挑这个坚持背后的假设（≤100字）。用户被动确认方案、没额外主张的，不拷问，直接定稿。

用户确认 → PLAN.md 定稿，commit（`docs: 方案定稿`）→ 进入 03。

## 修 bug

默认走 [轻档.md](轻档.md)：主会话复现、追根因、写任务文件和接口文件，限量测试代理写复现测试并锁定，开发代理再修。根因在架构上、要改接口契约、要动登录/密钥/权限代码的，回到本文件"中档走法"；碰数据结构或删除路径的走标准档。
